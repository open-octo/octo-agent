# 项目工作空间与源文件夹

`projects-design.md` 的后继。那份设计把项目定为「一个目录 + 在它上面干活的会话」；本设计把这两件事拆开：**项目 = 一个 octo 自有的工作空间 + 0..N 个源文件夹**。工作空间管 shell cwd、agent 产出和记忆作用域；源文件夹是项目引用的外部目录——代码仓库和资料文件夹一视同仁。

## 要解决的问题

「项目 ≡ 一个用户目录」在三个地方裂开：

1. **多仓库系统没有"对"的目录可选。** 一个微服务项目横跨五个仓库，项目目录设成哪个？选上层目录，env context 丢掉 git 语境、终端落在不是仓库的地方；选主仓库，其余仓库的知识无家可归。更糟的是碎片化：只要在任何一个子仓库里开过会话，就会为那个仓库裂出一个平行项目和平行记忆仓——同一个系统的知识散落在 N+1 个互相看不见的地方。
2. **agent 的产出弄脏仓库。** cwd = 仓库意味着草稿、报告、临时脚本全部落进仓库，git status 常年是脏的。
3. **记忆身份不稳定。** 记忆目录的 slug 挂在仓库路径上，仓库搬家或改名，记忆就成了孤儿。

答案的形状其实已经在代码里：定时任务的项目就是「`<workspace>/<任务名>` 自有目录 + 自己的记忆层」，只是源文件夹数为零。本设计把这个特例提升为一般形态——cron 项目从此和普通项目零差异。

## 模型

```go
type sessionGroup struct {
	ID         string   `json:"id"`
	Name       string   `json:"name"`
	SessionIDs []string `json:"session_ids"`
	Collapsed  bool     `json:"collapsed,omitempty"`
	TaskID     string   `json:"task_id,omitempty"`

	// WorkingDir 语义收窄为「项目的工作空间」：octo 在 <workspace> 下生成的
	// 自有目录，创建后不变。会话的 cwd、agent 产出、沙箱默认根都在这里。
	WorkingDir string `json:"working_dir,omitempty"`
	// SourceDirs 是项目引用的外部目录（仓库或资料夹），工具的额外可达根。
	SourceDirs []string `json:"source_dirs,omitempty"`
}
```

复用 `WorkingDir` 而不是新增字段，是因为所有解析代码（`resolveSessionDir`、`sessionCwdEnv`、记忆反查）无需感知这次语义变化——它们要的一直是「这个项目的会话在哪跑」，答案从用户目录变成自有空间，代码一行不改。

### 工作空间一律 octo 生成，没有用户自选路径

空间路径是 `<workspace>/<项目名>`，重名加后缀；创建后不变，改名只改项目名不动目录（cron 已有此先例）。不提供「把我的某个文件夹当空间」的选项，理由按分量排：

- **生命周期单形态。** 自有空间可以放心地删、回收、清扫：删项目 = 空间进回收站，孤儿空间定期清，一条规则。允许用户目录当空间，则每一处碰空间的代码——删除、回收站、清扫、迁移——都要先分辨「这是谁的目录」，且用户目录里混着用户自己的文件，动一下都是丢数据事故。这是每个未来改动都要付的税。
- **信任边界一句话讲清。** 写入之家永远是 octo 的地盘；用户目录都是显式挂载的引用。
- **记忆身份稳定**（见下——记忆实际挂项目 ID，但空间路径稳定让一切目录派生物都稳定）。

想让产物落在自己的文件夹里，在请求里说清楚落点即可——源文件夹本来就是可写的挂载。

### 源文件夹

- **仓库与资料夹不区分**，不嗅探 git：外部目录都是「引用」，挂载语义完全一致。
- **可被多个项目共享**——「订单重构」和「支付对账」都挂同一个服务仓库是正当诉求。
- 唯一校验：**不得位于工作空间根之下**。把 A 项目的空间挂成 B 项目的源文件夹会让目录→项目反查精神分裂，这一条在挂载时拒绝。
- **已知且接受的代价**：共享源文件夹的知识会在项目间重复——在 A 项目里学到「这个仓库构建前要跑 codegen」，B 项目的会话看不见，某天会再学一遍。这是「记忆坚持两层 + 源文件夹可共享」的必然推论。记忆**不做**第三层、不做沿目录树向上聚合：多层记忆的心智成本高于知识重复的成本。此段写明是为了防止将来有人把它当缺陷修出第三层来。

### 不做「产出目录」标记

曾经做过：给某个源文件夹打星标，env context 据此指示模型「成品写这里、草稿留工作空间」。删掉了，因为它只是一句 prompt 指示，而 env context 里「工作空间用于没让写别处的一切」这条更靠前、更绝对，任何没写死路径的请求都会被吸回 cwd——标记因此只在用户已经明说落点时才生效，而那种情况本来也不需要标记。想加固措辞就得把「默认落点」这件事整体交给模型判断，不确定性只是换了个地方。要产物落在哪，在请求里说。

定时任务显式配置的 `directory` 因此就是「挂载为源文件夹」，空间照常自有——cron 与普通项目没有任何分支。

## 会话的两种归宿

会话要么属于项目，要么是任务，没有第三态；「给单条会话自由选目录」这个概念从产品里移除。

- **项目会话**：cwd = 项目空间。在项目下创建的会话 `WorkingDir` 不 seed（现状即如此）。
- **任务**：创建时自动生成一次性空间 `<workspace>/tasks/<时间戳>`，写进 `Session.WorkingDir`。任务空间**不是项目**——不进侧栏项目列表、不建记忆层（任务记忆归全局层）。这替代了「所有任务挤在工作区根里」的现状，两条任务写同名文件互相覆盖的问题随之消失。删会话时其空间进回收站；启动时清扫指向已删除会话的孤儿空间。此前 seed 了工作区根的存量任务不迁移，按反转后的优先级继续跑在原地。

### 解析优先级反转

```
Session.WorkingDir（非空）  >  项目空间  >  全局工作区
```

`projects-design.md` 是项目优先。那个次序的动机——改项目目录要对全项目实时生效——随「空间创建后不变」而消失了；反转之后，CLI 在仓库里生的会话（见下）在**所有入口**都跑在那个仓库，跨入口漂移不再存在，Web 端也不需要任何例外。`resolveSessionDir` 仍是唯一裁决点，只是分支次序变了。

## cwd 语义与 env context

serve 侧的项目会话一律以空间为 cwd。env context 相应扩展：

- cwd 声明为「项目的 scratch / 产出空间」；
- 源文件夹清单：每个目录的路径、git 分支（若是仓库）、工具链;
- 进源文件夹干活靠模型自己 `cd` / `git -C`。

单仓库项目每条命令多一次 cd 是本设计接受的代价——它由模型付，不由用户付，env context 的措辞负责把错误率压下去。

**冻结身份**从 `(model, cwd)` 扩为 `(model, cwd, sourceDirsHash)`。增删源文件夹触发下一 turn 重新组装——与当年把 cwd 纳入判据是同构的第三个维度，机械扩展。

## CLI

CLI 的 cwd 是用户用 `cd` 亲手表达过的选择，终端尊重它：**cwd、hooks、沙箱根都留在终端所在地**（与今天一致），只有**记忆**一项归到项目。这是对「一切由同一个 cwd 派生」原则的唯一显式例外，且例外被限定为记忆这一项。

启动时按 cwd 反查归属，三态：

- cwd 被**恰好一个**项目的源文件夹引用 → 会话归入该项目，记忆走项目层；
- 被**多个**项目引用 → 弹选择器（复用 `-c` 选择器形态），选择记入会话；
- **无主**：cwd 是 git 仓库（本目录或祖先含 `.git`）→ 自动建项目 + 空间、cwd 挂为源文件夹；不是仓库 → 任务，记忆归全局层。

无主分支的 git 判定不是给项目分流形态（Web 端不嗅探 git），而是「值不值得为这个目录建项目」的门槛——`cd ~/Downloads && octo` 不应该在侧栏里留下一个叫 Downloads 的项目。这与「非 repo cwd 归全局记忆层」的既有判据同源。

反查因此是双轨的：cwd 命中某项目的**空间**（会话本来就在项目 scratch 里跑），或命中**源文件夹**（走三态）。前者永远唯一——空间不共享。

## 记忆

层级不变：**全局 + 项目**，两层。

记忆目录的 slug 从「挂空间路径」改为**挂项目 ID**：`~/.octo/memories/<Slugify(项目名)>-<id 派生哈希>`，名字部分生成一次、改名不动（与目录命名同一先例）。空间目录从此纯粹是 scratch，不携带记忆身份；项目无论怎么演化，记忆都跟着 ID 走。

## 信任与 hooks

- **添加源文件夹的动作本身就是信任授予**——UI 文案「添加 octo 可读取和编辑的文件夹」承载这层含义，不另弹确认框。挂载后该目录的 hooks / `.octorules` 全部加载；从项目移除即撤销。
- **加载顺序确定**：空间的先、源文件夹按挂载顺序，写死在实现里而不是依赖遍历序。
- **来源可见**：会话内能看到本轮加载了哪些目录的 hooks / octorules（env context 或启动日志列出），多目录叠加后行为可追溯。
- 沙箱与文件工具的边界 = 空间 + 全部源文件夹。

## UI

界面术语只有「项目」和「源文件夹」——"工作空间"是实现细节，不出现在任何用户可见的地方。

- **Composer chip「选择项目」**：不选 = 任务。下拉 = 搜索框 + 项目列表 + 「新建项目」 + 「打开本地文件夹」。
- **新建项目弹窗**：项目名 + 源文件夹（0..N，零文件夹允许创建——写作类、cron 类项目本来就是零挂载形态）。
- **「打开本地文件夹」是新建项目的速通**：选中文件夹直接创建（名 = basename、该文件夹挂为源文件夹），不弹窗。归属规则与 CLI 是同一张决策表：文件夹已被唯一项目引用 → 直接选中该项目而不是建重复；被多个引用 → 下拉就地收窄成候选项目让用户挑；无主 → 建。
- **项目设置弹窗**：入口在项目头 `···` 菜单，内容 = 改名 + 源文件夹增删。`projects-design.md` 删掉这个弹窗的理由是「目录不可改之后无事可做」；源文件夹的增删是真实且反复发生的操作（今天挂三个仓库、下月加第四个），理由失效，弹窗恢复。增删源文件夹触发 `sourceDirsHash` 重组，已有机制覆盖。
- **Composer 的目录 chip**：项目会话显示项目名，只读，语义不变。

## 迁移

启动 pass，挂在 `reconcileRegistry` 尾部，幂等：

1. **存量项目**（`WorkingDir` 指向用户目录）：生成 `<workspace>/<项目名>` 空间，原目录转为 `SourceDirs[0]`，`WorkingDir` 改指空间。cron 项目零迁移——它们的目录本来就是自有的，原地即空间。
2. **记忆目录搬迁**：旧的路径 slug 目录整体搬到新的 ID slug 目录，目标已有内容则不覆盖（`HomeDir` 的 legacy 迁移先例）。丢记忆比丢分组严重，这一步的防御是整个 pass 里最不能省的。
3. **行为回写**：旧项目目录写进每条成员会话的 `Session.WorkingDir`（仅为空者）。配合反转后的优先级，存量会话继续跑在它们一直跑的仓库里，**迁移零行为变化**；工作空间语义只对迁移后新建的会话生效。回写后的存量会话在形态上等同于 CLI 生的会话，不是新特例。

registry 的跨进程写入沿用既有的 `internal/lockfile` 文件锁，无新增要求。

## 测试要点

- 解析优先级反转：会话有自己的 `WorkingDir` 时压过项目空间；为空时落项目空间；无项目落全局工作区。
- 任务创建生成时间戳空间且不产生项目行、不建记忆目录；删会话空间进回收站；孤儿空间清扫幂等。
- 源文件夹挂载校验：工作空间根之下的目录被拒；同一文件夹可挂进两个项目。
- 「打开本地文件夹」三态：唯一引用选中既有项目、多引用给出候选、无主创建；均不产生重复项目。
- CLI 三态：唯一引用归入且记忆走项目层；多引用出选择器；无主 git 仓库自动建项目；非仓库目录记忆落全局。
- CLI 会话跨入口：在仓库里生的会话，Web 端继续跑在该仓库（不漂移到空间）。
- 冻结身份：增删源文件夹后下一 turn 重组，composed prompt 里的源文件夹清单跟着变；不变时复用冻结值。
- 记忆 slug 挂 ID：改项目名后记忆目录不动、继续命中。
- 迁移：存量项目获得空间、原目录降为源文件夹、记忆搬迁不覆盖已有内容、成员会话被回写后 cwd 与迁移前一致。
- hooks 加载顺序确定且来源在 env context 中可见。
- cron 显式 `directory` 落为一个源文件夹挂载，工作空间照常自有。
