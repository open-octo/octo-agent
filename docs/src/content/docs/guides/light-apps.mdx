When you ask the agent to generate an HTML page — a data reconciliation tool, format converter,
daily report template — and the task is **repeatable**, the agent will proactively suggest
saving it as a **Light App**. Once saved, you can open it anytime from the Web UI without
consuming LLM tokens.

## What it is

A Light App is an HTML page written by the agent using pure frontend technologies
(HTML + CSS + JS). It lives under `~/.octo/light-apps/`:

```
~/.octo/light-apps/<slug>/
├── manifest.json   # metadata: name, description, icon, created_at
├── index.html      # the page
└── …               # optional files it references by relative path: scripts, styles, images, fonts, models, media
```

Each Light App runs on its own origin (`<slug>.apps.localhost`), so it behaves like an ordinary
web page: `localStorage` persists between visits, downloads and fullscreen work, and files beside
`index.html` load by relative path. It cannot reach octo's own API, and it needs no backend.
Light Apps open only in a browser on the machine running octo — not on a phone over the tunnel.

## When to use

✅ **Good candidates for Light Apps**:
- Repeatable tools: data reconciliation, format conversion, CSV merging
- Template generators: daily report templates, checklist generators
- Tasks with fixed input → output rules: validators, calculators, formatters
- Tools you want available offline

❌ **Not suitable for Light Apps**:
- One-off analysis or research
- Tasks that genuinely need LLM reasoning each time
- Workflows requiring backend APIs / databases (use [Skills](/docs/guides/use-skills/) or [Workflows](/docs/guides/workflows/))

## How to create one

The agent automatically evaluates whether an HTML page is worth saving as a Light App. The flow:

1. You ask the agent to generate an HTML tool page in conversation
2. The agent generates and previews it, then proactively asks: "Save as Light App? Open anytime from the Light Apps panel with zero tokens."
3. On your confirmation, the agent writes both files to `~/.octo/light-apps/<slug>/` using `write_file`
4. The slug is derived from the app name — lowercase letters, digits, and hyphens only

You **don't need to touch the filesystem** — the agent handles everything.

## Managing Light Apps

Click "Light Apps" in the Web UI navigation bar to see a card grid of all saved apps:

- **Open**: renders the app in the Artifacts sidebar panel in preview mode — fully interactive
- **Edit**: opens an agent conversation with the current content inline, so the agent can update it
- **Delete**: removes the app after confirmation

Agent-generated HTML artifacts can also be saved to Light Apps with one click from the Artifacts panel.

## Mount it into the UI

A Light App normally lives on the Light Apps page and opens in the Artifacts panel. If you built
one you reach for constantly — a sketchpad, a calculator, a board — add a `mount` field to its
`manifest.json` and give it a permanent place in the interface.

```json
{
  "slug": "sketch",
  "name": "Sketchpad",
  "description": "A canvas for quick diagrams",
  "icon": "🎨",
  "mount": "view"
}
```

| `mount` | Where it shows up |
| --- | --- |
| *omitted* | The Light Apps page only — the default, and what every existing app does. |
| `"view"` | Its own entry in the left navigation, rendered full-page. |
| `"panel"` | A slot in the right-hand panel, alongside session artifacts and the diff review. |

This is a field you write by hand: the agent does not add it on its own, because whether an app
deserves a permanent spot in your UI is your call, not its.

Mounted apps are subject to the same locality rule as every Light App — they render from
`<slug>.apps.localhost`, which only resolves on the machine running `octo serve`. When you open
the Web UI from another device, mounted entries are hidden rather than shown broken. The Light
Apps page itself behaves the same as always.

### A complete example

A sketchpad that claims a page of its own. Two files, no build step:

```json
// ~/.octo/light-apps/sketch/manifest.json
{
  "slug": "sketch",
  "name": "Sketchpad",
  "description": "A canvas for quick diagrams",
  "icon": "🎨",
  "created_at": "2026-09-20T00:00:00Z",
  "mount": "view"
}
```

```html
<!-- ~/.octo/light-apps/sketch/index.html -->
<!doctype html>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<style>
  :root { color-scheme: light; --bg: #fff; --fg: #1d1d1f; --line: #0001; }
  :root[data-theme="dark"] { color-scheme: dark; --bg: #16181c; --fg: #e8e8ea; --line: #fff2; }
  body { margin: 0; height: 100vh; display: flex; flex-direction: column;
         background: var(--bg); color: var(--fg); font: 13px system-ui, sans-serif; }
  .bar { display: flex; gap: 10px; align-items: center; padding: 8px 12px;
         border-bottom: 1px solid var(--line); }
  canvas { flex: 1; touch-action: none; cursor: crosshair; }
  button { font: inherit; color: inherit; background: none; cursor: pointer;
           border: 1px solid var(--line); border-radius: 6px; padding: 3px 10px; }
</style>

<div class="bar">
  <input id="colour" type="color" value="#0e7490">
  <input id="size" type="range" min="1" max="24" value="3">
  <button id="clear">Clear</button>
  <button id="save">Save PNG</button>
</div>
<canvas id="c"></canvas>

<script>
  // The host passes the resolved theme on the URL, so the app can match the UI.
  const theme = new URLSearchParams(location.search).get('theme')
  if (theme === 'dark') document.documentElement.dataset.theme = 'dark'

  const c = document.getElementById('c')
  const ctx = c.getContext('2d')
  let drawing = false

  // Resizing clears the bitmap, so the strokes are re-drawn from the copy the
  // canvas held before the resize.
  function fit() {
    const snap = document.createElement('canvas')
    snap.width = c.width; snap.height = c.height
    if (c.width) snap.getContext('2d').drawImage(c, 0, 0)
    c.width = c.clientWidth * devicePixelRatio
    c.height = c.clientHeight * devicePixelRatio
    ctx.scale(devicePixelRatio, devicePixelRatio)
    ctx.lineCap = ctx.lineJoin = 'round'
    if (snap.width) ctx.drawImage(snap, 0, 0, snap.width / devicePixelRatio, snap.height / devicePixelRatio)
  }
  addEventListener('resize', fit)
  fit()

  c.addEventListener('pointerdown', e => {
    drawing = true
    c.setPointerCapture(e.pointerId)
    ctx.beginPath()
    ctx.moveTo(e.offsetX, e.offsetY)
  })
  c.addEventListener('pointermove', e => {
    if (!drawing) return
    ctx.strokeStyle = document.getElementById('colour').value
    ctx.lineWidth = document.getElementById('size').value
    ctx.lineTo(e.offsetX, e.offsetY)
    ctx.stroke()
  })
  c.addEventListener('pointerup', () => {
    if (drawing) { drawing = false; strokes++; publish() }
  })

  // ── Let the agent see this canvas ────────────────────────────────────────
  //
  // octo mirrors whatever an app publishes; the model reads it through the
  // lightapp_state / view_lightapp tools. One way: publishing describes the app
  // to the model, it grants the app no access to the conversation.
  let strokes = 0
  let publishTimer = 0
  function publish() {
    clearTimeout(publishTimer)
    publishTimer = setTimeout(() => {
      window.octo?.pushState({
        digest: strokes
          ? `A hand-drawn sketch, ${strokes} stroke(s).`
          : 'An empty sketch canvas — nothing drawn yet.',
        summary: { strokes },
        image: c,            // a canvas is accepted directly
      })
    }, 400)
  }
  publish()

  // ── Take what the agent sends ────────────────────────────────────────────
  //
  // The agent can hand this canvas an image (ask it to generate something from
  // your sketch). Draw it in, then publish again so the agent can see the
  // result of what it just sent.
  window.octo?.onDelivery(({ blob, note }) => {
    const img = new Image()
    img.onload = () => {
      // Fit inside the canvas, centred, without distorting the image.
      const scale = Math.min(c.clientWidth / img.width, c.clientHeight / img.height, 1)
      const w = img.width * scale
      const h = img.height * scale
      ctx.drawImage(img, (c.clientWidth - w) / 2, (c.clientHeight - h) / 2, w, h)
      URL.revokeObjectURL(img.src)
      strokes++
      publish()
      if (note) console.log('[octo]', note)
    }
    img.src = URL.createObjectURL(blob)
  })

  document.getElementById('clear').onclick = () => {
    ctx.clearRect(0, 0, c.width, c.height)
    strokes = 0
    publish()
  }

  // The plain <a download> idiom: the host turns it into a browser download or
  // the OS save dialog in the desktop app.
  document.getElementById('save').onclick = () => {
    const a = document.createElement('a')
    a.download = 'sketch.png'
    a.href = c.toDataURL('image/png')
    a.click()
  }
</script>
```

Reload the Web UI and **Sketchpad** is in the left navigation, with its emoji for
an icon. Change `mount` to `"panel"` and it moves into the right-hand panel's
switcher instead, beside session artifacts and the diff review.

The `window.octo.pushState` call is what lets the agent see the drawing: ask it
"what did I just draw?" and it reads the digest, then looks at the image. See
[Let the agent see inside](#let-the-agent-see-inside) below.

## Let the agent see inside

A Light App is sealed: it runs on its own origin behind a policy that closes
every network exit, so by default the agent has no idea it is open, let alone
what is in it.

An app can publish a snapshot of itself:

```js
window.octo.pushState({
  digest: 'A hand-drawn sketch, 3 strokes.',   // one line, written for the model
  summary: { strokes: 3 },                     // optional structured extras
  image: canvasOrBlob,                         // optional screenshot
})
```

The agent then has two tools: `lightapp_state` reads every open app's digest
(cheap, so it can check whenever you mention "my sketch"), and `view_lightapp`
pulls the screenshot into the conversation as a real image it can look at.

**Publishing gives your app nothing** — no conversation, no API, no
credentials. Call it whenever your state changes; octo coalesces pushes, so a
canvas firing on every stroke is fine.

### Taking what the agent sends

The agent can hand your app a file — ask it to generate a picture from your
sketch and it can put the result straight onto the canvas. Register a handler
to accept one:

```js
window.octo.onDelivery(({ blob, name, note }) => {
  // draw it in, display it, or ignore it — it is your app
})
```

This is the only inbound direction, and it carries a file and a note, nothing
else: no conversation, no instructions to execute. An app that registers no
handler simply never receives anything, and the agent finds out the same way it
finds out everything else about your app — by reading what you publish next.

The snapshot is held in memory only and disappears when octo stops or the app
closes.

## Technical constraints

The agent follows these rules when generating a Light App:

- Files the page needs live in the app's directory and are referenced by relative path; external scripts and stylesheets are allowed only from well-known CDNs (cdnjs, jsdelivr, unpkg, Google Fonts and their mainland-China mirrors) and are otherwise stripped
- The page's network is limited to its own files and those CDNs — no calls to other APIs, no images from other hosts, no access to octo's API
- File processing via `FileReader` + `<input type="file">`
- Saving results (a generated image, a converted file) via the standard `<a download>` idiom — the host writes the file: a regular download in the browser, the OS save dialog in the desktop app
- Icons via emoji or inline SVG
- Layout and color conventions from the `artifact-design` skill

The agent already knows these constraints — just describe what you want, and it handles the rest.
